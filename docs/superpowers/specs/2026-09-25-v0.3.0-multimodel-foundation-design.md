# Multi-model-per-simulation foundation — Design

**Date:** 2026-09-25
**Status:** Approved (owner) — ready for implementation plan
**Scope:** v0.3.0 remaining scope, sub-project 1 of 5. Prerequisite for GWE and PRT.

---

## Goal

Let one MODFLOW 6 simulation hold several models of different types
(`gwf`, `gwe`, `prt`, …) and let MCP callers address them with a
`component` selector — the internal plumbing the **GWE** and **PRT**
capability specs build on.

This sub-project ships **no user-facing capability**. It is validated by
internal tests. Its real validation is that GWE and PRT land on it and
pass their own closed-book rerun loops.

The v0.3.0 remaining scope (owner decision 2026-09-25) is
`GWE, PRT, MT3D-USGS` (and `MODPATH`, confirmed in scope), decomposed
into five specs built in order:

1. **Multi-model foundation** (this spec)
2. GWE
3. PRT
4. MT3D-USGS post-processing
5. MODPATH

---

## Current state (verified in source)

- `create_model` (`tools/builder.py`) builds one `MFSimulation` + one
  `mf6.ModflowGwf`, and registers the name → workspace mapping.
- `utils/model_store.py` caches **one `MFSimulation` per registered name**;
  `get_gwf(name)` returns `sim.get_model(name)` with a fallback to the first
  model in `sim.model_names`.
- Every builder tool resolves its target through `get_gwf(model)`;
  `summarise_model`, `model_status`, `_compute_model_status`, the runner's
  `.lst` progress/log reader, and `_find_output_file` / `_find_budget_file`
  all assume a single GWF model.
- `restore_oc_period_records` iterates **all** `sim.model_names` and applies
  GWF-OC-specific logic to each.
- `adopt_model` loads an existing simulation and caches it; the GWF name need
  not match the registered name.
- flopy 3.10 (installed) provides the full `ModflowGwe*` / `ModflowPrt*`
  package families and the `ModflowGwfgwe` / `ModflowGwfprt` exchanges
  (attached to the GWF model).

## Design

### Addressing model

- The MCP **"model" stays the simulation/workspace handle** (e.g. `myrun`).
- Model-scoped tools gain an optional `component: str = "gwf"` argument.
- Default `component="gwf"` reproduces today's behaviour byte-for-byte.
- Component names are discovered from the simulation, never hardcoded in tool
  signatures beyond the default. An unknown/absent component returns
  `INVALID_INPUT` naming the components actually present, e.g.
  `component 'gwt' not found; available: gwf, gwe`.

### Component registry — `utils/components.py` (new)

A registry plus resolver:

- `register_component(name, *, model_class, package_types, output_resolver=None,
  exchange_class=None)` — later specs (GWE, PRT) call this to teach the
  foundation about a component without editing foundation call sites.
- Built-in registration at import: `gwf → ModflowGwf`,
  `gwe → ModflowGwe`, `prt → ModflowPrt`, with `exchange_class`
  `ModflowGwfgwe` / `ModflowGwfprt` for the non-flow components.
- `model_class_for(component) -> type` — the FloPy model class.
- `resolve_component(sim, components_map, component) -> mf6.MFModel` — the
  live model object, raising a clear error for an unknown/absent component.
- `output_file(component, model, ws) -> Path | None` — the per-component
  head/output resolution hook. The default implementation is the existing GWF
  OC-filerecord + workspace-glob behaviour; a spec may register its own.

### Component map persistence — `.gwmcp_meta.json`

- `create_model` writes `components: {"gwf": <name>}`.
- `adopt_model` introspects `sim.model_names` and each model's type to build
  the map, so adopted simulations with arbitrary model names work.
- Component names for **new** models are short (`<base>_gwe`, `<base>_prt`),
  truncated to MF6's 16-character model-name limit; the meta map is the
  source of truth for resolution, so truncation never changes addressing.

### `utils/model_store.py`

- `get_model(name, component="gwf") -> mf6.MFModel` — resolves the MF6 model
  via the meta component map, then `sim.get_model(...)`.
- `get_gwf(name)` becomes a thin delegate to `get_model(name, "gwf")`
  (unchanged behaviour for every existing caller).
- `list_components(name) -> dict[str, str]` — the component → MF6 model-name
  map for a simulation.
- `_collect_input_files` already walks every `sim.model_names` + package, so
  staleness detection becomes multi-model-aware with no code change; a test
  locks this in.
- `_apply_meta_crs` applies CRS only to components that expose a `modelgrid`,
  skipping safely otherwise.
- `restore_oc_period_records` is gated to the `gwf` component (its
  external-OC period restore is GWF-specific); component OCs are handled by
  their own specs.

### `tools/builder.py`

- `create_model` unchanged except it writes the `components` map.
- New **internal** helper `add_component_model(model, component,
  grid_from="gwf")`:
  - creates the component model (`ModflowGwe` / `ModflowPrt`) in the same
    simulation;
  - **mirrors the GWF grid** into the component's grid package
    (`dis`/`disv`/`disu` — dimensions, `top`/`botm`, vertices/cell2d, `idomain`);
  - registers the exchange (`ModflowGwfgwe` / `ModflowGwfprt`) on the GWF model;
  - records the component in the meta map and stages via `save_sim`.
  - Deliberately internal: the GWE/PRT specs expose the user-facing
    `add_gwe_model` / `add_prt_model` tools that call it.
- `summarise_model` gains a `components` block: per component, the MF6 model
  name, package list, and grid summary. Top-level GWF fields are unchanged.
- `model_status` gains a `components` list. `next_steps` stays
  GWF-runnability-driven, guarded when no `gwf` exists; per-component hints
  are added by each spec.

### `tools/runner.py`

- Run stays **simulation-level** (`run_simulation` runs the whole
  `mfsim.nam`, which already includes every component).
- `get_run_log(model, component="gwf")` selects that component's `.lst`.
- Progress parsing (`_parse_mf6_lst_progress`) defaults to the `gwf` `.lst`;
  a component may be named explicitly.

### Error handling

| Situation | Result |
|---|---|
| `component` not present in the simulation | `INVALID_INPUT` with the available list |
| `get_model` on a component whose model is missing from `sim` | `MODEL_NOT_FOUND`-class error naming the simulation and component |
| Mutating a component of an adopted read-only model | unchanged `MODEL_ADOPTED_READONLY` |
| CRS apply on a component without a `modelgrid` | skipped, never raises |
| `next_steps` when the simulation has no `gwf` | omitted (no crash) |

### Backward compatibility

Purely additive: no signature removed, no default changed. `get_gwf` is a
delegate. `create_model`, `adopt_model`, and every existing tool call behave
exactly as before when `component` is omitted. The existing suite (482 tests)
must stay green **unchanged**.

## Explicitly out of scope

- GWE package physics (EST/CND/ADV/SSM/MWE/SFE/UZE/LKE/CTP) and SET temperature
  checks — GWE spec.
- PRT packages (PRP/MIP) and pathline/tracking readers/plots — PRT spec.
- GWT model support (architecturally reusable, not built here).
- Any temperature/pathline/tracking post-processing tool.
- Component-aware calibration (remains GWF-only).

---

## Testing

- **Unit — `tests/test_components.py`**
  - registry tables resolve `gwf`/`gwe`/`prt` to the right FloPy classes;
  - `register_component` extends the registry;
  - component-map persistence to `.gwmcp_meta.json`;
  - `get_model` resolution, `list_components`, unknown-component error;
  - `adopt_model` detection of component types.
- **Integration** — build a minimal two-model simulation (gwf + gwe with
  mirrored grid + exchange) via the internal helper, flush, reload from
  disk, assert `list_components` / per-component package access, and that the
  GWF-only path is unchanged.
- **Regression** — full suite green unchanged; `ruff` + `mypy` clean on
  touched files.
- **No closed-book rerun** — no user-facing capability ships here.

---

## Success criteria

1. A simulation can hold `gwf` + `gwe` (and later `prt`) models, each
   addressable via `component`, persisted across flush/reload/adopt.
2. `add_component_model` mirrors the GWF grid and registers the exchange.
3. Every existing tool call with no `component` is byte-for-byte unchanged;
   the full suite passes unmodified.
4. `summarise_model` / `model_status` report components.
5. The registry is extensible by later specs without editing foundation code.

# PRT (particle tracking) — Design

**Date:** 2026-09-27
**Status:** Draft — for owner review
**Scope:** v0.3.0 remaining scope, sub-project 3 of 5. Builds on the multi-model
foundation and follows the GWE sub-project.

---

## Goal

Add MODFLOW 6 particle tracking (PRT): build a PRT model that reuses the flow
grid, define particle release points, run the simulation once (flow then PRT),
and read/plot pathlines — all through MCP tools.

The v0.3.0 gate (owner decision 2026-09-25) requires PRT to be built **and** put
through the closed-book rerun loop (≥2 consecutive green, last
set-and-forget) against **`ex-prt-mp7-p01`** (owner decision 2026-09-27).

---

## Coupling architecture (owner decision 2026-09-27)

**Same-simulation GWF-PRT exchange, MF6-native.** PRT is a model inside the
flow model's existing `mfsim.nam`, coupled to the flow model by
`ModflowGwfprt`. This is the counterpart of GWE's FMI decision and is the
pattern the example scripts use.

Consequences:

- `add_prt_model(model)` creates a `ModflowPrt` model in the **same**
  simulation, mirrors the flow discretization, and registers the GWF-PRT
  exchange. The foundation helper
  `builder._impl_add_component_model(model, "prt")`
  ([builder.py:447](../../../src/groundwater_mcp/tools/builder.py#L447))
  already does exactly this — `add_prt_model` is a thin wrapper over it plus
  the PRT-specific setup below.
- The component is recorded in `.gwmcp_meta.json` as a **plain model name**
  (same simulation), not a `{"model", "workspace"}` derived-simulation entry.
  No `_component_cache` involvement.
- Workflow: a single `run_simulation(model)` runs the whole simulation; MF6
  orders GWF before PRT because of the exchange. The runner's separate-sim
  component loop (`component_sim_names`) does **not** see PRT, so there is no
  double run and no runner loop change.
- Grid tools already accept `component="prt"`; no new grid tool. PRT has
  DIS/DISV classes in flopy but **no DISU class**, so a DISU source grid is
  rejected clearly by `_mirror_grid`.

An FMI/derived-simulation PRT (reading a flow run's `.hds`/`.cbc`) is **out of
scope** for this sub-project.

## Target model

`ex-prt-mp7-p01` — the MODPATH 7 example problem p01 re-expressed with the
MF6-native PRT model (self-contained; no data directory). The closed-book
validation builds it from the published problem description via the MCP tools,
runs it, and compares the tracked pathlines/endpoints to the reference
solution. Target specifics are discovered during the validation session; they
do not constrain the tool surface below.

## Design

### `utils/components.py` / `utils/model_store.py`

No new registry work: `prt` is already registered
(`ModflowPrt`, DIS/DISV grids, `ModflowPrtoc`, `ModflowGwfprt`) and the same-sim
component path (`component_map` plain-name entries, `get_model(name, "prt")`)
already exists from the foundation. No model-store change is expected.

### `tools/builder.py`

- `add_prt_model(model)` — wraps `_impl_add_component_model(model, "prt")`.
  After the component exists it ensures the flow model exposes what tracking
  needs (a `_ensure_flow_saving_for_prt` guard, analogue of GWE's
  `_ensure_flow_saving_for_fmi`; the exact mandate — `save_flows` and/or
  `save_specific_discharge` on NPF and budget on GWF OC — is fixed by a short
  task-1 spike on a tiny model).
- `add_prt_mip_package(model, porosity, retfactor=1.0, izone=None)` —
  `ModflowPrtmip` (matrix input: porosity, retardation factor, zone array).
  Required for tracking.
- `add_prt_prp_package(model, release_points, release_times=None, boundnames=None, ...)` —
  `ModflowPrtprp`. `release_points` is the MF6 `packagedata` list
  (`(k, i, j, x, y, z, ...)` for DIS; `(x, y, z, ...)`/`(node, ...)` for
  DISV/DISU-free), and `release_times` the `release_timesrecord`.
- `add_prt_oc_package(model, track_filerecord=None, trackcsv_filerecord=None,
  track_release=None, track_exit=None, ...)` — `ModflowPrtoc`. The PRT OC
  records are tracking-oriented (no head/budget arrays), so it is a dedicated
  tool rather than an `add_oc_package(component="prt")` extension.
- Reuse `add_dis_package` / `add_disv_package` with `component="prt"` only if a
  user wants an explicit grid; `add_prt_model` mirrors it automatically.

### `tools/runner.py`

No loop change: PRT runs inside the single-simulation run. `run_simulation`
already returns per-model listing tails; the PRT `.lst` is the PRT model's
listing within `mfsim.lst`. `get_run_log(component="prt")` resolves from
`component_workspace` when present and otherwise falls back to `mfsim.lst`.

### `tools/postprocess.py`

- `read_pathlines(model)` — read the PRT track output. **Reader fixed by the
  task-1 spike:** flopy 3.10's `ParticleTrackFile` docstring claims MF6-PRT
  support but exposes no concrete PRT subclass, so the tool defaults to the
  **CSV track file** (`trackcsv_filerecord`, a text CSV with one row per
  particle per time) parsed with numpy/pandas; the binary `.trk` path is added
  only if the spike shows flopy reads it. Returns per-particle pathline arrays
  (particle id, time, x, y, z), summary statistics, and an `output_file`
  artifact, mirroring `read_heads`/`read_temperature`.
- `plot_pathlines(model, particles=None, ...)` — pathlines over the model grid
  (plan view) to PNG, the `plot_temperature_map` pattern.

### Error handling

| Situation | Result |
|---|---|
| `component="prt"` package before `add_prt_model` | `MODEL_NOT_FOUND` naming the missing component |
| DISU source grid for PRT | `INVALID_INPUT` (`_mirror_grid`: PRT has no DISU class) |
| release points outside active cells / malformed | `INVALID_INPUT` from MF6 precheck on run; surfaced in the run result |
| `read_pathlines` / `plot_pathlines` with no track output | `OUTPUT_FILE_MISSING` pointing at `run_simulation` |
| read-only (adopted) model | `ModelReadOnlyError` → `MODEL_ADOPTED_READONLY`, early guard as GWE |
| unknown component | `INVALID_INPUT` (foundation behaviour) |

### Backward compatibility

Flow-only usage is unchanged. `add_prt_model` only adds a model to an existing
simulation and records a same-sim component; every existing tool behaves as
before when no PRT component exists.

## Testing

- **Unit** — build a small flow model, `add_prt_model` (assert the PRT model,
  the mirrored DIS/DISV grid, the `ModflowGwfprt` exchange, and the components
  meta entry), then MIP/PRP/OC class and file assertions; `read_pathlines` on a
  synthetic track CSV; the error paths above.
- **Integration** — a tiny real-MF6 run (small DIS flow + a few release points)
  that terminates normally and produces the track output, proving the
  same-simulation workflow end to end; then `read_pathlines` + `plot_pathlines`.
- **Regression** — full suite stays green unchanged; `ruff` + `mypy` clean;
  flow-only behaviour byte-identical.
- **Closed-book validation** (release gate, separate session) — `ex-prt-mp7-p01`
  built, run and post-processed MCP-only, ≥2 consecutive green reruns, last
  set-and-forget.

## Explicitly out of scope

- FMI/derived-simulation PRT (no GWF-PRT exchange).
- DISU PRT grids (no flopy class).
- PRT calibration targets / sensitivity.
- MODPATH (legacy) — sub-project 5.
- MT3D-USGS post-processing — sub-project 4.

---

## Success criteria

1. A PRT model can be added to a built flow model, its grid mirrored and the
   GWF-PRT exchange registered, with `add_prt_model`.
2. MIP, PRP and OC are buildable and written correctly; release points and
   release times reach the PRT model.
3. One `run_simulation` runs flow then PRT and produces the track output.
4. `read_pathlines` and `plot_pathlines` work on that output.
5. Flow-only usage and the full suite are unchanged.
6. `ex-prt-mp7-p01` can be built, run and post-processed closed-book (gate).

# GWE (groundwater energy transport) — Design

**Date:** 2026-09-25
**Status:** Approved (owner) — ready for implementation plan
**Scope:** v0.3.0 remaining scope, sub-project 2 of 5. Builds on the multi-model foundation.

---

## Goal

Add MODFLOW 6 groundwater energy transport (GWE): build a heat-transport model
that reads a completed flow solution, run it, and read/plot temperature — then
validate it closed-book against the published **ex-gwe-radial** example.

The v0.3.0 gate (owner decision 2026-09-25) requires GWE to be built **and**
put through the closed-book rerun loop (≥2 consecutive green, last
set-and-forget).

---

## Coupling architecture (owner decision 2026-09-25)

**FMI (flow-model interface), matched to the target.** ex-gwe-radial does not
use a GWF-GWE exchange: it runs a **flow simulation** first, then a **separate
heat simulation** whose `ModflowGwefmi` package reads the flow run's
`GWFHEAD` (`.hds`) and `GWFBUDGET` (`.cbc`) files. The heat model is therefore a
*derived* simulation, not a coupled component in the flow `mfsim.nam`.

Consequences:

- A registered MCP model owns **two simulations**: the flow simulation (as
  today) and, once `add_gwe_model` is called, a heat simulation in a
  subdirectory. `model_store` caches the flow simulation under the registered
  name (unchanged) and the heat simulation under a component key.
- Workflow is **flow first, then heat**: `run_simulation(model)` runs the flow
  model, then the heat model, in order.
- A GWE model in its own simulation needs only one IMS, so the
  "different IMS per model" rule of the exchange mode does not apply (the
  published example still gives it its own IMS file).

An exchange-mode GWE (both models in one `mfsim.nam` with `ModflowGwfgwe` and
per-model `sim.register_ims_package`) is **out of scope** for this sub-project.

## Target model (verified from the published script)

`ex-gwe-radial` (Al-Khoury et al. 2020), scenario `ex-gwe-radial-slow-b`:

**Flow simulation** (`mf6gwf/`): TDIS 1 steady period; GWF with
`ModflowGwfdisv` (radial DISV mesh from `Qin100_V1e-5.csv`), `NPF`
(xt3d, `save_specific_discharge`), `IC`, `STO` (steady), two `CHD` packages
**with `auxiliary="TEMPERATURE"`**, `OC`.

**Heat simulation** (`mf6gwe.../`): its own TDIS (48 half-hour/day steps + 4
hourly), `ModflowGwe` with `Gwedisv` (same mesh), `Gweic`, `Gweadv`
(scheme TVD), `Gwecnd`, `Gweest`, **`Gweesl`** (the scenario's `neumann=100`
heat source at the borehole), **`Gwessm`** with
`sources=[("CHD-LEFT","AUX","TEMPERATURE"), ("CHD-RIGHT","AUX","TEMPERATURE")]`,
`Gweoc` (`temperature_filerecord=*.ucn`, `budget_filerecord=*.cbc`,
`saverecord={47: [("TEMPERATURE","LAST"),("BUDGET","LAST")]}`), and
`Gwefmi` pointing at the flow run's `.hds`/`.cbc`.

**Scope correction (target-forced, supersedes the earlier "core ADV/CND/EST"
answer):** the default scenario uses **ESL**, and the flow `CHD` carries a
temperature auxiliary that **SSM** consumes — so ESL and SSM are in scope, and
the GWF boundary tool needs CHD **auxiliary** support. `CTP` (the Dirichlet
variant) is deferred.

## Design

### GWE simulation and the model store extension — `utils/model_store.py`

- Component simulations are cached per registered name:
  `_component_cache[name][component] -> MFSimulation`. The flow simulation
  keeps its current cache and `get_sim(name)` behaviour.
- New `get_component_sim(name, component)` and
  `cache_component_sim(name, component, sim)`; `add_gwe_model` creates and
  caches the heat simulation.
- `flush_model(name)` flushes the flow simulation (as today) **and** any
  component simulations (writing the heat run's inputs into its subdirectory).
- The component map (`.gwmcp_meta.json` `components`) records the heat
  simulation's directory and its MF6 model name, so reload/adopt can find it.

### `tools/builder.py`

- `add_gwe_model(model, flow_model=None, sim_name=None)`:
  - creates an `MFSimulation` in `<workspace>/gwe/` with a `ModflowGwe` model;
  - builds `Gwefmi` from the flow run's `OC` head/budget filerecords
    (defaults to the registered model's flow `.hds`/`.cbc`);
  - records the component in meta; caches the heat simulation.
  - It does **not** mirror a grid: the heat grid is added explicitly with
    `add_disv_package(component="gwe")` (or DIS), so the target's DISV mesh
    from the CSV is reproduced exactly.
- `add_gwe_adv_package(model, scheme="TVD")`.
- `add_gwe_cnd_package(model, alh, ath1, ath2=None, alv=None, atv=None, ktw=None, kts=None)`.
- `add_gwe_est_package(model, porosity, heat_capacity_water, density_water=1000.0, heat_capacity_solid, density_solid, latent_heat_vaporization=None, ...)`.
- `add_gwe_ssm_package(model, sources=None)` — `sources` is the MF6
  `[(pname, srctype, auxname)]` list; validated against the flow model's
  boundary packages.
- `add_gwe_esl_package(model, stress_period_data, ...)`.
- Reuse `add_disv_package`/`add_dis_package`/`add_ic_package` with
  `component="gwe"`.
- Extend `add_oc_package` to `component="gwe"` through the registry
  (`ModflowGweoc`, `temperature_filerecord`, saverecord `TEMPERATURE`/`BUDGET`).
- **GWF-side:** extend `add_boundary_package` (`CHD`) to accept
  `auxiliary="TEMPERATURE"` with a 4th record column, so SSM has an auxiliary
  to mix.

### `tools/runner.py`

- `run_simulation(model)` runs the flow simulation first, then the heat
  simulation(s), aggregating success and listing files. `_impl_get_run_log`
  already takes `component`; the heat run's `.lst` is resolved from the
  component simulation.

### `tools/postprocess.py`

- `read_temperature(model, kper=None, layer=0)` — read the heat run's
  temperature output. **Reader resolved by a task-1 spike:** flopy 3.10's
  `MF6Output` has no `temperature()`; candidates are `flopy.utils.UcnFile`
  (the file is `*.ucn`) or a small custom reader over `BinaryHeader`. Returns
  the same shape/contract as `read_heads` (per-period 3-D array + metadata).
- `plot_temperature_map(model, kper=None, layer=0, ...)` — plan-view
  temperature; uses DISV cell x/y.
- `plot_temperature_timeseries(model, cells=[...], observed_csv=None, ...)` —
  temperature at cells over time, optional observed overlay (the
  `plot_subsidence` pattern).

### Error handling

| Situation | Result |
|---|---|
| `component="gwe"` packages before `add_gwe_model` | `MODEL_NOT_FOUND` naming the missing component |
| FMI flow outputs missing at heat run time | run reports failure with the flow listing appended |
| SSM `sources` naming a boundary absent from the flow model | `INVALID_INPUT` |
| `read_temperature` with no heat run output | `MODEL_NOT_FOUND`-class error pointing at `run_simulation` |
| Unknown component | `INVALID_INPUT` (foundation behaviour) |

### Backward compatibility

Flow-only usage is unchanged: `get_sim`, `run_simulation`, and every existing
tool behave as before when no GWE component exists. The model store keeps the
flow cache separate from the component cache.

## Testing

- **Unit** — build a small flow+GWE pair (DIS and DISV), assert each GWE
  package class and file, the FMI packagedata paths, the component map and
  component cache, `add_oc_package(component="gwe")` writing
  `temperature_filerecord`, CHD auxiliary records, and `read_temperature` on a
  synthetic/small run.
- **Integration** — a tiny coupled run (GWF then GWE-FMI) that terminates
  normally and yields a temperature file, proving the two-simulation workflow.
- **Regression** — full suite stays green unchanged; `ruff` + `mypy` clean.
- **Closed-book validation** — the ex-gwe-radial rerun loop (fetch
  `Qin100_V1e-5.csv`, build the DISV grid via `gridprops_file`, build the flow
  model, build the heat model with FMI, run both, read temperature and compare
  the borehole/radial profile to the reference columns).

## Explicitly out of scope

- Exchange-mode GWE (`ModflowGwfgwe` in one simulation).
- `CTP` (constant-temperature / Dirichlet variant).
- `SFE`/`UZE`/`LKE`/`MVE`/`MWE`/`GWE-GWE` advanced packages.
- Temperature calibration targets and sensitivity.
- GWT (solute) — separate v0.2.0/v0.3.0 item.

---

## Success criteria

1. ex-gwe-radial can be built, run (flow then heat) and post-processed closed
   book, producing a temperature field that matches the reference profile.
2. Each GWE package (`DISV`/`IC`/`ADV`/`CND`/`EST`/`ESL`/`SSM`/`OC`/`FMI`) is
   buildable and written correctly; `temperature_filerecord` is populated.
3. The flow model keeps its current behaviour; the full suite passes unchanged.
4. `read_temperature`, `plot_temperature_map` and `plot_temperature_timeseries`
   work on the target output.

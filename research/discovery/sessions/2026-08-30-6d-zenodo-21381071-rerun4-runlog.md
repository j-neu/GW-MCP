### 8.1 Toolchain finding — external K array
The adopted model read K inline (NPF rewritten by add_npf_package). For a template to drive K, the model must read an external array:
- `add_npf_package` accepts only a number or array (a filename string is rejected by the schema) — it cannot express an external reference.
- `setup_pest_control` did **not** rewire NPF k to the template target.
- `setup_calibration(parameterisation={"k": {"target": "npf:k", "scope": "all", ...}})` **does** rewire NPF k to an external `OPEN/CLOSE` array
  (`gwf0_k.dat`) and writes a space-free forward wrapper (`gwmcp_run_0205c1.py`) — required here because the model workspace path contains spaces.
- After the rewire, `setup_pest_control` was re-run with the 18-zone template targeting `gwf0_k.dat`, `noptmax=3`, and the wrapper as the model
  command. The 18-zone template is sensitive again because the model now reads `gwf0_k.dat`.

The template-token delimiter finding: tokens must be delimited by the character after `ptf` (e.g. `~name~` for `ptf ~`), not by `@`; the tool
parses `ptf~` (no space) as an invalid header. Wide `~    name     ~` tokens are accepted and are needed to avoid value truncation.

**Root cause of the slow/failed forward runs — template line length.** The initial 18-zone template wrote one grid row per line (1,252 fixed-width
fields ≈ 26 KB/line). When pestpp substituted the template, the resulting `gwf0_k.dat` had exactly 2,003,200 whitespace-delimited values but with
26 KB lines, and MF6's array reader hit `end-of-file during read, unit 1009, file gwf0_k.dat` — verified by running mf6 directly on the same
values in different line layouts: 26 KB lines → EOF error; ~10 values/line (flopy-style) → normal termination. This caused every pestpp forward run
to fail/hang after the first realisations. Fixed by regenerating the template with 10 fields per line and 24-char fields (token `~`+24-char+`~`),
which pestpp substitutes into a readable array.

**Second root cause — the Python forward wrapper hangs under pestpp.** setup_calibration had generated a forward wrapper (`gwmcp_run_0205c1.py`,
a venv-python → uv-python → mf6 chain) because the workspace path contains spaces. Under pestpp-ies 5.2.16 in this environment, the wrapper's
`subprocess.run([mf6])` never spawned mf6 (both python processes sat at 0 CPU for 10–20 minutes, no mf6 child), stalling every forward run. Manual
launches of the same wrapper from a console ran fine, so this is pestpp/console-environment-specific. The fix was to set the model command to the
direct mf6 executable (`C:\Users\jakob\.local\bin\mf6.exe`) via `pestpp_options["model_command"]` — pestpp then runs mf6 with cwd set to the model
directory and forward runs start within seconds. (An experiment with `num_workers=2` also showed that two concurrent forward runs in the shared
workspace clobber each other's outputs, so `num_workers=1` is required.)

### 10.2 Final configuration and scoping

Because the shipped ×0.1/×10 parameter bounds drive the IES initial ensemble (par_sigma_range=4 → σ_log ≈ ln(100)/(2·4) ≈ 0.58), the
ensemble-0 realisations perturbed zone K by factors up to ~10×, which the strongly-nonlinear Newton/unconfined model cannot integrate quickly
(25+ min/run vs 2 min for the base). The bounds were scoped to base×0.5–base×2 (σ_log ≈ 0.17, zone-K factors 0.5–1.6×) — a documented
deviation from the shipped pst bounds, made to keep forward runs tractable. `ies_initial_ensemble` cannot be used to control the draw with this
pestpp version. num_workers must be 1 because the MCP-generated forward wrapper hard-codes the model workspace, so in-place runs must be serial.
`noptmax=2` bounds the iteration count; the base parameter values sit at the optimum (phi≈0), so IES should terminate after 1–2 iterations.

## 12. Deviations / decisions / gaps

- **Payload**: 2 M-cell K array could not be passed inline to `add_npf_package`; equivalent zone-based assignment used (`assign_k_from_zones`).
- **Parameter bounds scoped** from the shipped ×0.1/×10 to ×0.5/×2 to keep IES forward runs tractable (see 10.2); the base values are unchanged.
- **Template**: tokens must use the `ptf` header delimiter (`~name~` for `ptf ~`, not `@`), be wide enough to avoid value truncation, AND produce
  MF6-readable array files — one grid row per line (26 KB lines) causes `end-of-file during read` in MF6's array reader; ~10 values per line works.
- **Forward command**: the MCP-generated Python wrapper (for space-containing workspaces) hangs under pestpp-ies 5.2.16 here (mf6 never spawns);
  the direct `mf6.exe` model command works. `num_workers` must be 1 (in-place runs clobber each other's outputs otherwise).
- **`++ies_initial_ensemble` is rejected** by pestpp-ies 5.2.16 (`control file parsing error: the following '++' args were not accepted`).
- **noptmax=0** makes pestpp-ies run only the control-file base run (no ensemble); noptmax≥1 is required for the ensemble.
- **IES update iteration aborted** (see 10.3) — the updated parameter ensemble is numerically intractable for this strongly nonlinear model;
  the iteration-0 initial-ensemble result is reported instead.
- **External K**: `add_npf_package` cannot express an external file reference and `setup_pest_control` does not rewire NPF k; `setup_calibration`
  was used purely to rewire the NPF to the external array, then `setup_pest_control` configured the 18-zone calibration. This is an MCP-tool-only

- **Pseudo-observations**: values taken from the shipped reference output (model's own reference), documented above; not field data.
- **CRS**: nominal EPSG:32618 assigned so spatial joins / obs mapping use the model's own XORIGIN/YORIGIN coordinate space.
- Prior-attempt artefacts in the dataset directory were left untouched unless they were the files the adopted model reads.

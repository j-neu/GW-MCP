## Root-cause investigation of the calibration stall

Two distinct failure modes were found, in order:

1. **Forward-wrapper FIFO deadlock (fixed, `f1e7015`).** `_generate_forward_wrapper` emitted
   `subprocess.run([MF6], cwd=WS)` with no stdio redirection, so MF6 inherited PEST++'s FIFO stdout.
   MF6 writes its console listing there — the 158-period H201 listing is **657 KB** against a **64 KB**
   Windows pipe buffer — so once PEST++'s serial run manager stopped draining the pipe, MF6 blocked
   forever: the wrapper parked at `mf6_start`, pestpp spun at 100 % CPU, no phi. Reproduced
   deterministically by running the generated wrapper with an undrained stdout pipe (**hung at 25 s**
   before; **completes <1 s** after detaching the streams). MF6 already writes its full listing to
   `<gwf>.lst`, so the console streams are discarded.

2. **MCP-tree launch latency (open, environment).** After the fix, under the VS Code-spawned MCP
   server each forward `mf6` launch still takes **51 / 81 / 144 / 245 / 267 s** (once ~12 min) while
   MF6 reports `Elapsed run time 0.095–0.158 s`, and pestpp spins at 100 % CPU with no `mf6.exe` in
   the process table. Evidence it is the MCP tree, not MF6/PEST++/the model:
   - `mf6.exe -v` = 0.05 s; `start_run()` through the MCP server = 0.14–0.16 s (same binary/workspace).
   - The **same** `pestpp-ies <case>.pst` run directly from a shell completes a 4-real IES in
     **9.6 s** with **40** `mf6_done` events (and 36.8 s on the rerun-4 copy) — no latency.
   - An A/B harness mimicking the MCP server (outer process with an undrained stdin pipe and
     `CREATE_NO_WINDOW`, spawning pestpp exactly as `runner._run_process` does) did **not** reproduce
     it: inherit-pipe-stdin **11.3 s** vs `stdin=DEVNULL` **10.6 s**.
   - Most likely a Windows **Job Object / process-creation limit** on the extension's children (or
     endpoint protection on that tree).

   Consequence: IES/GLM never finish an iteration; PEST++ degrades silently (only "failed to compute
   parameter derivative" warnings, `.sen` keeps just `k33`, no `.phi.actual.csv`). The best GLM
   attempt reported a base phi of **285.023** before stalling.
